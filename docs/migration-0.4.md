# 0.4 工作区迁移与中断恢复

0.4 打开既有工作区时会检查 `.parrhesia/state.sqlite3` 的数据库格式，必要时迁移或恢复查询索引。正常使用已有工作区入口即可触发，不需要逐个输入案例 ID，也不需要手工修改数据库版本。

数据库格式与案例证据协议是两件事：SQLite `PRAGMA user_version` 当前为 `3`；案例自身的 `schema_version`、`gate_version`、冻结输入及其摘要保留原值。索引重建不会把旧案例升级为新科学结论，也不会补填用户接受或审查结果。

## 从 0.3 升级前

关闭正在写入该工作区的宿主/命令，备份完整工作区状态、原始证据文件及旧版安装包。不要只复制仍在写入的 SQLite 主文件而遗漏 WAL 等关联状态。先在备份副本上打开 0.4，核对案例列表、关系、冻结摘要和既有报告，再切换实际工作区。

0.4 的 `record-exec` 默认类别为 `auto`/`unknown`，执行日志不再默认证明 benchmark 或研究设计。2×2 统计源在手动登记和显式导入中都受到类别及公式绑定约束；旧冻结源若存在不相容类别会返回 `artifact_kind_conflict`。此时保留原案例，另建案例以受支持类别登记统计补充来源并提供独立设计证据。Fisher 的有限精度/工作量边界与历史公式数值变化见[导入说明](artifact-ingestion.md)；不改写旧冻结数字来通过新核验。

需要回滚时，使用升级前的完整工作区副本和与其匹配的旧版包；不要让旧程序直接写入新版本已经修改的工作区，也不要手工降低 `user_version`。将升级后的工作区另行保留，避免丢弃期间新增的案例或证据，再明确处理需要迁移的新增内容。

## 兼容范围

自动综合仅合并明确关联、范围与估计目标兼容的比较。缺少源区间覆盖率的历史效应仍保存在旧案，并在综合的 `excluded_ineligible` 报告。旧案冻结记录无需回填。LaTeX 已展开的稿件需用新版 `draft_manuscript` 返回的合成摘要重新进行预填绑定。多工作表预填要显式传入 `sheet_name`。历史结局标签与分值不一致时，重新计算的校准报告保留原值和冲突状态，并排除该分值。

| 数据库格式 | 打开行为 |
| --- | --- |
| `0`、`1`、`2`，具有受支持的历史结构 | 在一个事务内创建所需结构、回填索引，完成后设置为 `3`。空的新数据库从 `0` 初始化。 |
| `3`，尚无本次索引维护完成标记 | 从案例原文一次性重建索引，修复旧版可能留下的空表或残缺索引。 |
| `3`，已完成维护且索引正常 | 使用增量维护，不逐个解析整个工作区的案例原文。 |
| 其他版本，包括负数和未来版本 | 返回 `unsupported_database_version`，不执行迁移、不降低版本、不接受写入；只读报告入口也拒绝解释未知格式。 |

版本号被识别为历史版本不表示任意数据库内容有效。损坏的 JSON、案例键与正文身份不一致、缺失的必要字段或不兼容的表结构仍会使启动失败；失败时不猜测或改写证据。

## 原子性与已形成残缺索引的恢复

迁移先取得 `BEGIN IMMEDIATE` 写事务，再检查版本与结构。表和触发器创建、索引回填、完成标记及版本更新在同一事务内提交。回填第一条、中间条或最后一条时发生异常，均回滚本次迁移；解除故障后重新打开工作区会重试。

旧版中断可能只留下索引表而没有索引行。案例原文仍在，但列表和关系图可能无法发现它们；按已知 ID 读取案例曾可能逐个恢复。0.4 不再以“索引表存在”推定回填完成，而使用 `storage_metadata` 中的 `index_maintenance_revision=1` 完成标记。缺标记、缺索引表、旧版本或缺案例摘要时，会从 `cases.document` 重建 `case_summaries`、`case_links` 与 `evidence_index`。完成标记是内部缓存维护信息，数据库容器格式仍为 `3`。

新触发器也会将索引行的直接 SQL 插入、修改或删除标为待修复；随后打开工作区或进行索引查询会从案例原文恢复对应行。正常索引更新在三张投影表全部完成后清除待修复标记。

恢复仅修改派生索引和数据库维护信息。已有案例正文、证据快照、事件行及其哈希链、导出内容保持原样；已记录的证据类型限制保留，只补回能够从案例原文恢复的缺失限制。历史未哈希事件仍保留其原有状态，不会被迁移包装成已验证事件。

## 升级或恢复遇到错误时

1. 遇到 `unsupported_database_version`，使用能读取该版本的发行版，或恢复自己保存的兼容工作区副本；不要手动降低 `user_version`。
2. 遇到迁移中断，解除磁盘、锁或其他实际故障后重新打开工作区。成功后通过案例列表和关系图核对预期案例，不需要先知道各个 ID。
3. 遇到原始内容损坏或身份不一致，保留数据库和完整错误，从已有备份核对；索引恢复不能重造缺失的证据或原始案例。

已有 Engine 实例每次打开连接也检查版本；若另一进程恰在检查后、事务前升级到未知格式，提交前的检查会拒绝并回滚该事务。只读快照在其读取事务内检查版本，保持只读。

## 已验证范围

新增 `tests/test_storage_recovery.py` 覆盖首次/中间/末次回填故障、修复自身中断、旧版空/残索引、三类索引损坏、受支持版本迁移、未知版本和并发升级、既有证据类型限制保留，以及正常启动不全量回填。失败迁移和未知版本拒绝的测试比较数据库原始字节；恢复成功的测试比较案例、事件、快照、导出内容与索引一致性。

2026-11-17 本地结果：新增恢复测试 **10/10**、既有事件链测试 **8/8**、分发与只读报告测试 **15/15** 通过。原实现的失败记录和修复后的记录分别保存在 `review/release-repair-2026-11-17/storage/`，原测试与旧审计材料未改写。

这些检查验证 SQLite 异常回滚与重新打开的行为；未模拟物理断电、磁盘损坏或网络文件系统。能够直接修改数据库、移除触发器并伪造维护标记的同权限进程，不在索引恢复所提供的防护边界内。迁移通过也不替代冻结内容校验、宿主验收或真实作者收益评测。
