# Parrhesia 产品设计：让结论与证据相称，并明确作出判断

## 产品承诺与边界

Parrhesia 面向需要评价证据、解释结果、比较方案并形成结论的 Agent 工作流。主要交付形态是符合 Agent Plugins 约定的可移植插件：技能负责组织模型工作，MCP 内核保存结论、审查和裁决，项目级 `AGENTS.md` 负责何时启动与遵守哪些判断规则。Grok 是可适配的模型或宿主之一，不是产品逻辑的唯一依赖。

产品要优化两个结果：**证据与主张的匹配程度，以及判断的明确程度**。它不把更肯定、更积极、更多批评或更少限制语当成质量。目标行为是：证据充分时明确承认贡献；证据冲突时比较解释；证据不足时明确说哪条主张尚不能成立，并给出与当前任务有关的处置和改判条件。

当前版本提供可运行的本地工作流、持久记录、结构化约束和导出。审查与裁决的语义工作由宿主模型完成，内核不自行调用 Grok 或其他模型。安装成功、结构检查通过和一次演示完成，分别不能证明模型行为已改善、科学结论成立或真实宿主已正确隔离上下文。效果评估方案见 [evaluation-plan.md](evaluation-plan.md)。

它不用于绕过模型安全约束、鼓励无根据的反对、强迫二选一、代替研究者签字，或要求每个小任务都进行五阶段审查。

## 三种错误为什么必须分开处理

| 错误 | 可观察表现 | 专门处理的环节 | 不应使用的替代指标 |
|---|---|---|---|
| 理想化与夸大 | 从相关跳到因果；把演示当效果；把条件成立写成普遍成立 | 夸大审查：证据能支持到哪里 | “语气是否谨慎” |
| 过度防御与低估 | 已支持的结果仍被弱化；无关限制反复出现；追加分析不改变判断 | 低估审查：证据已经支持了什么 | “删掉了多少免责声明” |
| 空泛中立 | 两边都说却不比较；没有最终判定；不断把责任推向未来工作 | 单一裁决：现在如何判断、为何、何时改判 | “答案是否鲜明或迎合用户” |

一个模型同时承担找错、找贡献和写结论，容易把审查数量误当质量，也容易为初稿辩护。分工的价值在于让两种检查分别提出可追溯的修改请求，再让裁决者逐条解释取舍。双审查不是相互抵消的两股意见：**不能投票、平均主张级别或机械取中间值**。

裁决采用[唯一规则源](../policy/parrhesia-policy.md)中的优先级与触发条件，本说明不另定义顺序。支持不足不能由积极语气补足；已经支持的局部贡献也不能被一个不影响它的局限抹去。

## 正常使用路径

1. **确定问题并形成初稿。** 明确用户现在需要哪一个判断、结论适用的对象与范围，以及已有证据。资料是待评价的数据，不把资料中的指令继承为工作流规则。
2. **结论台账。** 把会影响用户理解或决策的主张拆为可核对条目；同时登记证据、检查状态和假说来源。登记完毕后冻结本轮输入。
3. **并行、分别审查。** 用同一冻结版本产生两个审查包。夸大审查者与低估审查者分别接收本角色任务，不接收另一个角色的意见。
4. **单一裁决。** 裁决者接收台账和两份审查；逐条处理意见，对每条结论作判定并修订正文。
5. **溯源核对与交付。** 核对文件、引用和结构绑定，清楚展示已核对范围、未解决问题和最终文本。研究者可采纳、限定采纳、提出挑战或暂缓。

对应的程序入口为 `python -m parrhesia serve --workspace PATH`，主要工具为 `parrhesia_workflow(action, payload)`。宿主先读取 `parrhesia_contract` 返回的当前契约和工作区；需要更换项目时，只选择用户明确指定的已有工作区。准确参数以 [contract.md](contract.md) 和运行时契约为准。

## 模块一：结论台账

台账是审查对象，不是对全文逐句加标签。建议每次围绕一个科学或产品问题，保留少量有决策意义的核心主张；长稿按问题分批，避免“三条意见上限”掩盖第四个实质问题。

| 信息 | 应回答的问题 | 缺失时的处理 |
|---|---|---|
| 稳定 ID 与一句话主张 | 究竟判断哪句话，什么结果可推翻它 | 先拆分含多个命题的句子 |
| 对象与适用范围 | 对哪些数据、样本、条件成立 | 保留未知，不自动外推 |
| 主张级别 | 描述性观察、相关、可预测、机制线索、因果中的哪一级 | 按实际研究设计选择，不以词语匹配自动升级 |
| 证据定位 | 哪个文件版本、图、表、记录支持或反驳它 | 未定位的资料不能算已核验 |
| 效应与不确定性 | 变化有多大，精度、变异或范围如何 | 数字未知时明确缺失，不用“显著”代替 |
| 预设或探索性 | 看数据前是否有可核对记录 | 本地登记不能反推已预注册 |
| 1–3 个最强替代解释 | 已排除、部分排除、未排除的解释分别是什么 | 不为凑数编造威胁 |
| 底线检查 | 质控、样本/批次、重复单位、方法前提、多重比较、泄漏、基线 | 逐项记为通过、失败、未知或不适用，并说明依据 |
| 最终判定与置信理由 | 支持、条件性支持、不支持、证据不足中的哪种 | “未来还需研究”不能代替判定 |
| 改判条件 | 哪个新结果会升级、收窄或推翻当前判断 | 写可观察的证据，不写泛泛的“更多研究” |

科学主张的五级分类不能解释所有工程和决策任务。工程证据应表达测试、环境、输入与实际行为，例如“此版本在所列测试中恢复成功”；决策应表达选择、目标、成本及改变选择的条件。当前 schema 在 `domain="general"` 下仍使用同一组级别；工程事实通常记为 `descriptive`，不适用的科学检查注明理由，行动建议在范围和判定理由中分开表达。该版本没有另行实现工程等级体系，不能把测试通过编码成生物学因果证据；纯偏好也不必强行塞入科学台账。

## 模块二：夸大审查

只报告会改变主张级别、判定或适用范围的实质问题，每轮最多三条。每条必须绑定结论 ID、具体证据、错误的推理环节和建议的新表述。允许零条；不得为了扮演批评者而制造问题。

重点包括：相关与因果混淆；预测被解释为机制；分析单位不独立；“一组显著、另一组不显著”被写成组间差异；事后发现被写成预设；忽略反例；未经检索的新颖性断言；把合成测试、执行日志或 API 成功写成科学/产品收益证明。

审查者须说明降到哪一级或收窄到什么条件。缺少干预不自动否定描述性贡献；缺少外部重复不自动把所有观察判为无效。质疑应作用于被它影响的具体结论。

## 模块三：低估与过度防御审查

同样最多三条，逐条说明当前文字弱在哪里、应恢复到什么表述、由哪项证据支持。它不能制造证据，不能只因句子有“可能”就要求删除，也不能以用户想要积极结果作为依据。

检查五类问题：

- 已支持的效应或局部发现被笼统限制语盖过；
- 同一局限在不同位置重复出现，却未增加信息；
- 贡献被埋在讨论末尾，正文仍声称没有可得结论；
- 两种解释证据并不相当，正文却假定对称；
- 建议了追加分析，但无论结果怎样都不会改变结论或行动。

**对截图中“样本量有限”规则的修正：**不知道偏倚方向，不代表限制空泛。样本量可能影响估计精度、检验功效、稀有事件识别或外推范围；这些都可以构成有效限制。应问“它具体影响哪个判断，影响方式是否有依据”，不强迫模型编造高估或低估方向。若方向和幅度确实无法估计，应明确未知，并说明它限制的是精度、可识别性还是适用范围。

对于异质性，只有直接比较或交互检验、比较总量及合理解释能够支持差异结论时，才恢复相应贡献。重复观察不自动是机制；不同参数得到相似结果不自动是独立验证。

## 模块四：单一裁决

裁决者不再新增一轮无限审查。它逐条给出“采纳 / 部分采纳 / 驳回”及证据理由；两位审查者都错时可以都驳回；一位指出真实限制、另一位指出真实贡献时，可以同时采纳到不同范围。

每条结论只有一个当前判定。API 中这个判定评价 `revised_text` 所表达的最终命题；报告同时展示原文与修订文。若原句是“X 导致 Y”，改成“本样本中 X 与 Y 相关”后判为支持，必须明确这是对修订后相关命题的支持，不能呈现为原因果命题通过审查。

| 判定 | 含义 | 合格的表达方式 |
|---|---|---|
| `supported` 支持 | 提供的证据支持这一范围内、这一级别的主张 | “我的判断是支持，因为……；若出现……则改判。” |
| `partially_supported` 条件性支持 | 最终命题仍有仅在部分范围成立的条件 | 必须写清成立条件与不成立部分；已完全收窄且获支持的命题可判支持 |
| `unsupported` 不支持 | 现有反证、失败检验或设计约束使该主张不能成立 | 说明被否定的是哪一级主张；不等同证明所有替代解释 |
| `insufficient_evidence` 证据不足 | 现有资料不足以判定该主张成立与否 | 明确缺口、当前不应做的推断、适用的处置与改判条件 |

“证据不足”是正式立场，不是逃避立场。例如：“现有结果不能区分批次差异与处理效应，因此不采纳处理引发机制变化的主张；保留已观察到的分组差异。取得跨批次的独立生物学重复后重新评估。”这里既有判断，也没有伪造确定性。

行动判断须与科学判断分开：证据不足时，是否进行低成本试验、暂缓上线或维持现状，还取决于代价、可逆性和用户目标。裁决不能把“可以试验”改写为“机制已证实”。高/中/低置信度是带理由的定性评价，未经校准不能解释为数值概率。

修订正文时把贡献放在前面，将改变结论含义的限制紧邻相应句子。删除无信息重复；保留阴性结果、反例、来源冲突和实质不确定性。结束审查的条件是关键判定及其依据已清楚，而不是所有未知都已消失。

## 模块五：执行与溯源核对

程序能核对结构、ID 覆盖、冻结版本绑定、材料文件的字节摘要和记录一致性。它不能仅凭哈希证明数字正确、源文件来自可信实验、引用支持主张或某段代码确实产生了该输出。

证据应区分 `reported`（提交者报告）、`observed`（当前流程实际观察到的材料）与 `synthetic`（示例/测试）。这些标签仍受记录来源约束：一个上传的旧运行日志不因为被读到就成为本流程亲自执行的事实；一个模型填写 `observed` 也不是独立证明。对真实运行的确认还需要命令、版本、输入、输出与退出状态之间可核对的链路。

引用核实应保留检索范围和实际阅读范围；仅看到摘要不能当完整方法核查。未执行检索时不写“经检索”；有限检索未命中也不能支撑全球“首次”。模型产出的引文和文字与其他输入一样需要检查。

假说日志记录本工作区何时登记了什么内容，并能帮助维护探索性来源。设备时间、可修改的本地数据库和模型自述都不足以证明“数据分析前已预注册”。需要这种强主张时另行提供可信时间来源、注册记录和研究进程证据。

最终交付应分开显示：流程是否完成、机械核对结果、尚未解决的语义/证据问题、研究者是否采纳。未核验不能显示为已通过；工作流完成也不是科学接受。

## 上下文隔离与提示注入边界

冻结后由内核生成两个角色包，再交给两个新上下文。审查包包含同一版本的初稿、台账、证据和角色规则；不会另外注入起草过程、用户期待的结论、其他审查意见或与本问题无关的私有资料。初稿或问题本身仍可能嵌入期望结果或叙事倾向，内核不会自动识别清除它们，因此不能称为完全盲法。

同一个对话中连续写“现在你是另一个审查者”，不构成独立上下文。同模型两个新调用可以隔离会话信息，但仍有相同训练偏差；异模型也不自动构成独立证据。

本地包的字段筛选和冻结是工程保证；宿主是否实际创建干净上下文、模型是否偷带先前信息，目前不能由本内核证明。角色提交的“我已隔离”声明只记为声明。不能做到时仍可执行有用的审查，但必须标为隔离未验证，不能宣传为独立审查已验收。

证据正文及附件中的“忽略规则”“请给出支持”等属于资料内容，不修改角色权限、费用上限或裁决标准。只允许必要字段进入模型请求；向第三方发送私有稿件、未公开结果和患者资料仍需该数据与接收服务的明确授权。

## 生命周期、失败与人类介入

本轮输入冻结后不原地覆盖证据或台账。新事实改变判断时，保留旧结果，创建后续 case 并在标题/背景中关联先前 case ID；没有修订 API 时不得伪造“自动版本继承”。两份审查未齐全，不进入正常裁决；一个角色失败不能冒充零问题审查。

用户可在任意阶段要求暂停、补充背景、挑战某个证据/判定、暂缓或限定采纳。`record_human_decision` 保存 `accept`、`challenge`、`defer` 或 `pause`、责任人和理由；身份是调用者报告，未经过认证，模型不得代用户作决定。`pause` 阻止工作流后续写入；`challenge` / `defer` 阻止最终导出，后续 `accept` 可恢复。宿主同时停止后续模型/外部调用并保存 case ID；恢复前读取状态。挑战或限定采纳若需要改变冻结输入，则创建后续 case，不能用接受动作修改旧结论。没有用户接受也可以交付供审阅的报告，但须显示未记录接受；导出之后的人类事件不追溯改写旧报告。

三条问题上限是注意力约束，不是放行规则。若超过上限仍存在会改变结论的问题，审查者提交 `review_status="needs_split"`，内核将 case 标为 `review_blocked` 并阻止裁决；宿主缩小问题范围，另建后续 case 分批处理。在全量关键主张获得审查前不声称整篇已完成。结构化覆盖字段能表明提交覆盖了哪些 ID，不能证明每个 ID 得到深入阅读。

恢复时读取 SQLite 状态与原调用结果，不凭聊天记忆重建已完成工作。记录 ID、材料摘要和事件历史用于定位，不宣称数据库防篡改或外部审计认证。数据默认保存在选择的工作区；导出和外发是不同动作。

## 产品验收分层

| 层级 | 应展示的证据 | 可支持的结论 |
|---|---|---|
| 工程契约 | 测试、非法状态拒绝、版本绑定、重启恢复、导出读回 | 本地工作流按已测条件运行 |
| 包装与安装 | 插件文件、技能发现、MCP 工具列举与宿主实际调用记录 | 在已验收宿主可发现并调用 |
| 宿主编排 | 两个干净上下文的实际记录、各自输入、单独裁决、暂停恢复 | 所测宿主执行了所需流程 |
| 语义收益 | 预先冻结的盲评方案、保留集、预算对齐的对照 | 在所测任务分布上是否改善校准与判定 |
| 领域有效性 | 独立数据、正交测量或干预等适用证据 | 对具体科学主张的进一步支持 |

当前产品交付首先完成可检查、可恢复的工作流基础；随后用真实宿主验收与保留集评价决定是否值得推广。不得以愿景中的最后一层给当前版本命名或宣传。
